# Принятые решения

Формат: вопрос → решение → почему.

### 1. Где лежат send.php и config?
**Решение:** `send.php`, `config.example.php`, `.htaccess` лежат в корне проекта рядом с `index.html`; настоящий `config.php` создаёт покупатель, он в `.gitignore`. `send.php` ищет конфиг в `LANDING_CONFIG` (для тестов), рядом с собой и на уровень выше.
**Почему:** покупателю проще загрузить одну папку целиком. Вариант «на уровень выше публичной папки» описан в README как самый безопасный; `.htaccess` закрывает `config.php` на Apache.

### 2. Минимальное время заполнения: как мерить без расхождения часов?
**Решение:** клиент отправляет `elapsed` (миллисекунды с момента показа формы), а не временную метку. Сервер сравнивает с `min_fill_seconds`.
**Почему:** часы на устройстве посетителя могут отличаться от серверных; разница «сейчас минус метка» дала бы ложные отказы. Робот может подделать значение, но это стандартный уровень защиты для формы без бэкенда с сессиями; от настойчивой подделки защищает лимит частоты.

### 3. Поле-ловушка: что отвечать роботу?
**Решение:** при заполненном скрытом поле `website` обработчик отвечает `200 {ok:true}` и ничего не отправляет.
**Почему:** робот не получает сигнала, что его заметили, и не подбирает обход.

### 4. Лимит частоты в Worker
**Решение:** если в `wrangler.toml` включён биндинг `RATE_LIMITER` (Cloudflare Rate Limiting, период только 10 или 60 с), используется он; иначе — запасной счётчик в памяти экземпляра. В PHP — файловый счётчик с блокировкой `flock`.
**Почему:** биндинг по документации «допускающий» и работает отдельно в каждой локации, а в память экземпляра на Cloudflare рассчитывать нельзя. Но без аккаунтных настроек такой лимит всё равно лучше, чем ничего. Это записано в README. Ключ лимита — IP (`CF-Connecting-IP`).

### 5. Формат сообщения в Telegram
**Решение:** `parse_mode=HTML`, все введённые данные проходят через экранирование `&`, `<`, `>`, `"`, `'`; управляющие символы вычищаются, длины ограничены; `link_preview_options.is_disabled=true`.
**Почему:** HTML проще и безопаснее Markdown(V2) в плане экранирования; поле `link_preview_options` — актуальная замена `disable_web_page_preview`. Фейковый Telegram API в тестах отвергает невалидную разметку, как настоящий.

### 6. Откуда берётся список услуг в форме?
**Решение:** JS собирает варианты из заголовков карточек раздела «Услуги»; в HTML остаётся один вариант «Нужна консультация».
**Почему:** покупатель правит услуги в одном месте и не рассинхронизирует список.

### 7. Как «удаление секции не ломает меню»
**Решение:** меню строится из `main [data-nav]`; ссылки `href="#id"` на несуществующие секции скрываются скриптом; бургер не создаётся при пустом меню. Автотест удаляет каждую секцию (и все сразу) и проверяет отсутствие ошибок, мёртвых якорей и горизонтальной прокрутки.
**Почему:** это прямое требование ТЗ.

### 8. Меню без JavaScript
**Решение:** меню строится JS-ом, без JS видны только логотип и кнопка «Записаться».
**Почему:** ТЗ требует автоматическое построение меню; страница остаётся читаемой и единой прокруткой.

### 9. Палитры и тёмная тема
**Решение:** палитры — переменные `light-dark(светлый, тёмный)`; тема следует настройке устройства, её можно зафиксировать `data-theme`. Три палитры × две темы проверены скриптом контраста (WCAG AA 4.5:1 для всех пар текст/фон).
**Почему:** общие требования просят проверку в светлой и тёмной теме; `light-dark()` поддерживается всеми современными браузерами и сокращает CSS вдвое.

### 10. Фото в демо
**Решение:** все фото — с Wikimedia Commons (CC BY / CC BY-SA), только руки и ногти, без узнаваемых лиц; сертификаты нарисованы мной. Источники — в `img/CREDITS.md` и REPORT.md.
**Почему:** выдуманного мастера нельзя «одевать» в фото реального человека; руки с маникюром нейтральны. Лицензии CC требуют указания авторства — оно в CREDITS.md, лицензии и в README напоминание заменить фото.

### 11. Карта
**Решение:** `<div class="map" data-src="…">`, iframe создаётся при приближении блока к экрану (IntersectionObserver, запас 300 px). В демо — адрес виджета Яндекса с координатами; настоящий код конструктора покупатель подставляет в `data-src` (инструкция в README).
**Почему:** у меня нет аккаунта Яндекса для создания именной карты; формат `map-widget/v1` тот же, что в конструкторе. Карта проверена в браузере.

### 12. Демо-режим без правок рабочих файлов
**Решение:** рабочий `js/config.js` содержит `demo: false`. Скрипт `scripts/build-demo.sh` собирает `_site/`, включает `demo: true`, подключает `demo/demo.js` и `demo.css` (переключатель палитр, предпросмотр сообщения Telegram), подставляет адрес. Workflow GitHub Pages запускает этот скрипт.
**Почему:** переключатель палитр должен быть виден только в демо, а покупатель получает чистый сайт без демо-кода. Пуш и репозиторий не создаются — по запросу.

### 13. Общие требования про Docker, Python, pytest, ruff, vitest
**Решение:** не применимо (ТЗ шаблона: чистые HTML/CSS/JS без Docker). Вместо pytest — `node:test`; вместо ruff — проверка синтаксиса и тестов. Docker использован только для локальной проверки `send.php` на PHP 7.4 и 8.3.
**Почему:** раздел шаблона приоритетнее общих требований.

### 14. `docs/ADMIN.md`
**Решение:** админки нет, поэтому `ADMIN.md` — памятка владельцу: как приходят заявки, что менять, что не трогать, что делать при утечке токена.
**Почему:** общие требования называют этот файл обязательным; смысл адаптирован.

### 15. policy.html без noindex
**Решение:** убрал `noindex` с политики.
**Почему:** Lighthouse SEO на странице с `noindex` падает до 63; политика в индексе не вредит.

### 16. Версии GitHub Actions
**Решение:** `actions/checkout@v7`, `configure-pages@v6`, `upload-pages-artifact@v5`, `deploy-pages@v5` — актуальные мажорные теги репозиториев на момент работы (проверено `git ls-remote`).
**Почему:** требование сверять версии с актуальными.

### 17. Права/лицензия
**Решение:** LICENSE.md — заготовка с пометкой «проверит автор».
**Почему:** так сказано в общих требованиях.
